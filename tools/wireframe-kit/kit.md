# Wireframe kit — L0

An L0 wireframe is grey boxes plus one annotation chip per field. The chip carries the data
contract: point id, unit, provenance, current storage and disposition. An engineer reading
the mockup can tell which data point a field is and whether it exists today.

There is no shared CSS. Every `.mockup.html` carries the style block below inline. Copy the
block; do not import it.

## 1. Scope rules

- Greyscale only. No surface palette, no status colour. Colour reads as a design decision.
- One `.mockup.html` per feature and surface. Every state on the same page, stacked, each
  under a labelled state strip. No tabs, no JavaScript routing, no hidden states.
- Fictional data only. Never copy a name, number, amount or document id from a screenshot.
- Do not invent navigation. Label a screen with no current equivalent `NEW SCREEN NEEDED`.
- A fixture is a labelled example, never a verified calculation, a working integration or
  approved policy.
- The wireframe explains the flow. It is not a source of business rules; the PRD is.
- Customer surfaces: write the copy in English and mark every string that will be localised
  with `[customer language]`. Internal surfaces ship in English.

## 2. Field annotation chip

Every field that displays, captures or derives a value carries one chip:

```
[ POINT-ID · unit/type · provenance · current storage · disposition ]
```

Each segment maps to a column of the feature's `internal/data-packet.csv` (`point_id,label,type_unit,provenance,current_storage,disposition,surface,notes`).

| Segment | Packet column | Rule |
|---|---|---|
| `POINT-ID` | `point_id` | Must be a row in the packet. Form `ABC-01`; the prefix groups points (`DOC`, `RWK`, `PRV`, `AUD`) |
| `unit/type` | `type_unit` | Shortened. Keep the unit or the enum: `hours`, `₹`, `enum: unreadable \| mismatched \| missing` |
| `provenance` | `provenance` | One or more of the origins below, shortened to the one that applies on this screen |
| `current storage` | `current_storage` | A reuse location: column, JSONB path or configuration item. `none — no current path established` where none exists. Abbreviate long paths; never change the claim |
| `disposition` | `disposition` | Exactly the packet's value |

**Provenance** — where the value originates.

| Value | Means |
|---|---|
| `customer` | Entered by the customer on the customer surface or by message |
| `ops` | Entered by an ops role on the internal console |
| `field` | Captured on the field app by a field verifier or referral agent |
| `document` | Read from an uploaded document |
| `provider` | Returned by an external provider or partner |
| `derived` | Computed or generated by the system from other points |
| `config` | A configuration value the product or ops lead sets |
| `backfilled` | Filled for cases that exist before the feature lands |

**Disposition** — what this feature does with the point.

| Value | Means |
|---|---|
| `reuse` | The point exists and is shown as it is |
| `extend` | The point exists; the feature adds a value, a surface or a role to it |
| `proposed new` | No current path. The feature introduces the point |
| `configure` | A configuration value the product owns; it may not exist yet |
| `derive` | Computed from other points; nothing new is captured |
| `unresolved` | The owner has not decided where the point lives |

Examples from the worked feature:

```
[ DOC-02 · enum: received | accepted | unreadable | mismatched | missing · ops · h_document.status · reuse ]
[ RWK-02 · enum of case-record fields · ops · none — no current path established · proposed new ]
[ RWK-07 · days left · derived · derived — h_rework_item.raised_at + window · derive ]
```

Markup: `<span class="chip">…</span>` inside `<div class="f">`, after the label and value.
A field with no chip, or with two, is a defect. Product names a storage location it found;
it never designs one.

## 3. State strips

Every state block opens with one strip. The six states are not interchangeable.

| Strip | Means |
|---|---|
| `EMPTY` | Nothing captured yet. Distinct from zero |
| `PARTIAL` | Some required values present, the rest outstanding |
| `MISSING` | A required value is absent and the absence is the fact to show. Never rendered as `0` or `—` |
| `RESTRICTED` | The value exists but this role may not see or act on it |
| `PROVIDER-FAILED` | A provider attempt ran and returned no usable result: pending, no match, expired or errored. Never rendered as a successful zero |
| `REWORK` | The value was returned for correction: who asked, why, and what reply is expected |

A screen that cannot reach a state records `not applicable on this screen` under the strip
with the reason. Every file shows all six strips.
Markup: `<section class="state"><div class="strip">MISSING</div> … </section>`.

## 4. Naming conventions

| Thing | Convention |
|---|---|
| File | `products/<code>/<feature>/mockups/<surface>-<feature>-v1.mockup.html`; a new version is a new file |
| Page title | `<feature> — <surface> · <outcome> · L0 data contract` |
| Frame and state ids | `id="<surface>-s1"` for a screen; `id="<surface>-s1-missing"` for a state block |
| Screen heading | `S1 · <screen name>`, then actor, entry and exit on one line |
| Fixtures | `Customer A`, `Customer B`; roles for staff; round money `₹5,00,000`; references `CASE-REF-0001`, `DOC-REF-0001`, `PRV-REF-0001` — never a real-looking UUID |
| Shells | customer web `.frame.page` (480 px); field app `.phone` (360 px); console `.cols` |

## 6. Required page furniture

Every mockup opens with an HTML comment carrying the artifact frontmatter (`status`,
`version`, `supersedes`, `decision_refs`, `why`, `last_updated`), then a legend naming:

1. the feature, the surface, the outcome, and the context version it was drawn against;
2. the `current-behaviour.md` rows or screenshots it was drawn against, with date — or the
   statement that no reference exists and the screen is held;
3. `Greyscale wireframe. Fictional data. Fixtures are labelled examples, not verified
   calculations, approved policy or working integrations.`;
4. the chip format from section 2 in `<code>`, never in a live `.chip` span.

## 7. Verification hook

`python3 tools/wireframe-kit/check_wireframe_data.py <feature-folder>` fails with `file:line`
when a chip does not resolve, a field has other than one chip, a strip label is outside the
six, or a chip's disposition or storage claim disagrees with the packet. See `README.md`.
