# `.mcp.json` — the two servers and why the SQL runner is not one

Open a session, run `/mcp`, and authorise each server once. Nothing else is needed.

## The entries

| Key | What it is | Transport | Authorisation |
|---|---|---|---|
| `tracker` | the issue tracker's hosted MCP server, reached through `mcp-remote` | stdio, `npx -y mcp-remote https://mcp.linear.app/mcp` | OAuth in the browser on first `/mcp`; the token is stored by the CLI, not in this file |
| `analytics` | the event-analytics MCP server | HTTP, `https://mcp.posthog.com/mcp` | login on first `/mcp`; the server routes to your data region |

The keys are capability names on purpose. Tool names derive from them —
`mcp__tracker__…`, `mcp__analytics__…` — so skills and reviewers refer to "the tracker" and
"event analytics" and keep working when you swap the vendor behind a key.

`.mcp.json` holds no secrets. Commit it.

## Swap in another tracker

Replace the `tracker` entry; keep the key. Three common shapes:

```jsonc
// 1. A hosted server that speaks Streamable HTTP natively (no mcp-remote needed)
"tracker": { "type": "http", "url": "https://<your-tracker>/mcp" }

// 2. A local server from a package
"tracker": { "type": "stdio", "command": "npx", "args": ["-y", "<package-name>"] }

// 3. GitHub Issues: no MCP server required — the `issue-tracker` skill's GitHub adapter
//    uses the `gh` CLI through Bash. Delete the `tracker` entry and set `_tracker: github`
//    in `_profile.md`.
```

The `issue-tracker` skill reads `_tracker` in `_profile.md` to choose its adapter; the MCP
entry only has to exist for the adapter that needs it.

## Why `mcp-remote` for the tracker

Some clients only speak stdio. `mcp-remote` bridges a hosted HTTP server to stdio, so the same
`.mcp.json` works in every client this pack targets. If your client supports Streamable HTTP
directly, shape 1 above with `https://mcp.linear.app/mcp` also works.

## Why the SQL runner is not an MCP server

`tools/query/run-sql.sh` is a script, not a server, and that is deliberate.

1. The API key stays in your shell environment. An MCP server would need it in a config file
   or a server process, and either is one step closer to a commit or a log.
2. The read-only guard is a few lines of bash you can read. A guard inside a server is a
   promise you cannot inspect from the session.
3. A script runs where the data-analysis skill can see every statement it sends, print the
   dry run, and stop on a 404. That is the behaviour the pack's data rules depend on.

The query API the script talks to is described in `tools/query/README.md`. Which source to
use for which question is in `tools/query/sources.md`.

## If a server fails to connect

Treat it as a connection failure, not a missing capability. Run `/mcp` to re-authorise. Check
`npx` is on the `PATH` for the `tracker` entry. Do not paste tokens into this file.
